PACKING IMPROVEMENT PLAN
========================

Goal: combine the pieces that already exist into one loop with feedback,
instead of a straight line of independent passes.

PHASE 3 FIXED CREVICE SET (current procedure, per user):
  1. After Phase 1, compute the crevice field ONCE (ComputeCreviceBaseline):
     cleaned VoidField mask + spots, keep spots with width 0.2-3cm (S0).
     Each mask voxel is assigned to its nearest spot (distance to inscribed
     sphere); in-range spots' voxels form C0.
  2. Targets come only from S0, never regenerated -- small fruit must not
     create targets for later small fruit. Attraction target = spot center
     offset 1cm away from the container wall (unchanged).
  3. Each round recomputes the current field ONLY to test closure: a spot is
     closed once < creviceClosedFrac (0.5) of its C0 voxels are still open.
  4. Open spots: TryFillSpot with small kinds, sizeMustFitLocalWidth=false,
     at most creviceMaxAttemptsPerSpot (3) attempts per spot.
  5. Metric (ComputeCreviceCoverage -> crevice_coverage.txt): C0 volume
     closed/still open, new void outside baseline, and per Phase 3 fruit the
     C0 volume it closed (nearest fruit surface within 1cm). Closed <
     creviceUsefulVolume (0.05 cm^3) = unnecessary fruit.
  Result on melone_test from the 39-instance Phase 1 pack (2026-09-26):
    old (regenerated spots): 258 fruit, 159 unnecessary, C0 closed 30.0 of
      206.5 cm^3, 31/161 spots closed, new void 146.6 cm^3, 330 s.
    new (fixed S0):           96 fruit,   3 unnecessary, C0 closed 31.2 of
      206.5 cm^3, 31/161 spots closed, new void 104.3 cm^3, 108 s.
  Open issue: 130/161 spots stay open, most run out of attempts.

PHASE 3 SHRINKWRAP-SURFACE REWORK (2026-09-26, per user): VoidField's
"worth filling" test is volumetric (raw dist kept wherever closed<=0, i.e.
the WHOLE interior of the closed hull) -- caught by the
blueberry1_001-on-fig1 case: spot 4 had a big VoidField radius (1.11cm)
purely because fig1's own surface is ~0.95cm from the spot CENTER while
nothing else is nearby, but at fig1's own outer skin there was nothing to
bridge at all -- a lone convex fruit's flank, not a crevice. User's
correction: Phase 3 should only ever attract fruit to points ON the
shrinkwrap's own surface that are not already covered by a single bigger
fruit's surface -- never volumetric interior. Rejected surface-mesh +
point-sampling as the mechanism (extra geometry step, resampling
artifacts, harder to subgrid later); instead added ComputeShrinkwrapField
(PackShrinkWrap.h/.cpp): same two grids ComputeShrinkWrapDistField already
builds for the shrinkwrap mesh (closed + raw, one call, shared grid), kept
raw's value only where |closed| <= voxelSize (a thin shell AROUND the
zero crossing = the skin itself, not the volume behind it), blocked
elsewhere -- same shape/sentinel as VoidField, so ExtractVoidSpots (
threshold+morph-open+distance-transform+local-maxima+NMS) runs on it
completely unchanged. Wired in by swapping the one ComputeVoidField call
inside PackingDriver.cpp's ComputeCurrentVoid (the single chokepoint
ComputeCreviceBaseline/PackFillCrevices' closure test/ComputeCreviceCoverage
all go through) to ComputeShrinkwrapField -- everything downstream of that
helper is now skin-based with no other code changes needed.
ComputePackQuality's own openVolume metric deliberately still uses the
volumetric ComputeVoidField (a global fillable-space number, not a Phase 3
target list).

  CORRECTED MENTAL MODEL (user correction, supersedes step 9's framing
  above for Phase 3 specifically): small fruit is not supposed to FIT
  inside a wall crevice -- it is supposed to REST ON TOP of one, bridging
  its mouth, shrinking a large cavity down to something small enough to
  ignore at manufacturing time. Tiny bespoke blueberry tiers are explicitly
  NOT wanted (hard to manufacture, bloat mesh size). This means step 9 (a
  floor-sized tier) is the WRONG lever for Phase 3; the right lever is
  letting Phase 3 place existing small-fruit kinds even when they are
  bigger than the crevice.
  DONE: TryFillSpot gained a sizeMustFitLocalWidth parameter (default true,
  Phase 2's behavior unchanged); PackFillCrevices passes false. This is the
  SAME parameter name/idea as the very first TRIED AND REVERTED entry
  above, redone now that the two defenses that disaster was missing are
  both in place: kindsBySize scoped to the small-fruit categories (so a
  container-sized "watermelon" mesh cannot be reached), and a real
  container-containment check (ContainerOutsideFraction, tightened this
  round to kContainerOutsideThresh=0.05 from 0.5 -- 0.5 was never actually
  validated, it just happened not to matter while sizeMustFitLocalWidth was
  always true).
  Removing the fit filter exposed a SECOND, deeper defect that had nothing
  to do with size-fit directly: EnvelopeOccupiedFraction measures UNSIGNED
  distance from the candidate's own surface samples to the nearest existing
  fruit surface, merged across all instances. Unsigned distance cannot tell
  "far from any surface because free" from "far from any surface because
  deep inside one" -- and cannot see overlap AT ALL from the side of an
  existing instance the candidate fully swallows (the swallowed instance is
  nowhere near the CANDIDATE's own surface, so the candidate reads as
  clear). This was invisible under sizeMustFitLocalWidth=true (a
  size-bounded candidate is always close to scale with its gap, so its
  whole body sits near a boundary somewhere) and only surfaces once a
  candidate is free to be bigger than its neighbors. First measured
  result: fill_fraction read 118.7% of container volume -- physically
  impossible, i.e. real, severe, silent overlap.
  DONE (two new checks, PackingDriver.cpp):
    - SignedOverlapFraction: fraction of the CANDIDATE's own samples that
      land inside any nearby EXISTING instance's OWN per-kind SIGNED sdf
      (queried directly, instance by instance, via broad phase) -- replaces
      EnvelopeOccupiedFraction in the POST-settle acceptance gate (the
      pre-settle cheap check still uses the unsigned field as a fast,
      approximate first pass; only the check that actually decides
      commit needs to be exact).
    - EngulfsExistingInstance: true if any nearby EXISTING instance's
      CENTER lands well inside the CANDIDATE's own sdf -- covers the
      opposite direction SignedOverlapFraction cannot (existing instance
      swallowed somewhere in the candidate's interior, away from the
      candidate's own surface). Only run when sizeMustFitLocalWidth=false.
  Iterated three times against melone_test's real fill_fraction number:
  118.7% -> 109.2% (tightened thresholds alone) -> 102.0% (added
  EngulfsExistingInstance) -> 78.9% (swapped in SignedOverlapFraction for
  the acceptance gate). 78.9% fill / 4.5% open is the first result that is
  both physically sane (<100%) and a real win over the pre-Phase-3-rewrite
  baseline (45.6% fill / 34% open) -- exactly the "shrink big cavities into
  small ignorable ones" outcome the user asked for.
  Performance side effect, also fixed: with the fit filter gone, every kind
  in kindsBySize gets tried at every spot, and the new post-settle checks
  reject most of them -- but paying for a full physics settle (up to 30-137
  steps under the N2 extension) only to reject anyway made crevice rounds
  balloon from ~4s to 45+s as fewer spots stayed claimed. Fixed by adding
  a SECOND, PRE-settle call to SignedOverlapFraction/EngulfsExistingInstance
  (on the unsettled starting pose, with a much looser threshold, 0.6 vs the
  0.15 acceptance threshold -- loose enough that physics still gets to
  fix a moderate starting overlap, tight enough to kill hopeless ones
  before ever calling NudgeToTarget). melone_test total Phase 3 time with
  everything above: 137s over both small-fruit categories, 138 placed,
  bounded and finite (no runaway), down from need-to-kill-the-process
  before this fix existed.

  1. "raspberry2_106 ... half-way inside another fruit." SignedOverlapFraction

     CORRECTED MENTAL MODEL above: Phase 3 target selection (ExtractVoidSpots

     both wall and fruit) or near a lone fruit's convex surface but far

     Measured on melone_test: fill 77.1%/open 5.0% (102 vs 131 fruit placed

     NOT done / still open: this still does not distinguish a genuine

  THIRD ROUND: user reported raspberries STILL half-inside plum after fix
  #1 above (SignedOverlapFraction / ExistingInsideCandidateFraction). Root
  cause was not in either check's logic -- it was in the DATA they read.
  MeshInfo::ComputeSDFCached (MeshInfo.cpp) builds each item KIND's own
  per-instance sdf as a NARROW-BAND field: FastSweepPar was called with a
  fixed band=8 voxels, valid only within ~1.6cm of the mesh surface for a
  plum-scale item (voxSize 0.2cm). Beyond that band, GetCoarseDist returns
  AdapDF::MAX_DIST -- a large POSITIVE "far/unswept" sentinel, indistinguishable
  from genuinely outside. Both overlap checks test dist<0 for "inside," so
  a raspberry buried more than ~1.6cm into a plum read as NOT inside,
  silently. (There was even a commented-out CloseExterior call in this
  function, suggesting the incompleteness was already half-noticed.) The
  container's own sdf (ComputeSDF, PackingScene.cpp) never had this problem
  because it already uses band=1000 (effectively unbounded).
  DONE: sized MeshInfo::ComputeSDFCached's FastSweepPar band from the
  mesh's own extent (ceil(maxLen/voxSize)+4) instead of a fixed 8, so the
  sweep reaches every item's full interior regardless of size. One-time
  cost per kind (cached), same reasoning the container path already uses a
  large band for.
  Measured: fill 67.3%/open 10.1%, 104 placed (run_log11.txt) -- similar
  aggregate numbers to before, expected since this bug only affected
  candidates overlapping LARGER existing fruit specifically, not most
  placements. NOT independently re-verified with a rigorous mesh-accurate
  check yet -- a rough sphere-distance sanity check on raspberry-vs-plum
  pairs still flags a few as close, but average-radius spheres are too
  crude a proxy for irregular/elongated fruit shapes to be decisive. Next
  step if this resurfaces: query TryFillSpot's actual SignedOverlapFraction
  directly on the specific flagged instance pair rather than a standalone
  geometric approximation.

IMPLEMENTATION ORDER
---------------------
Dependency order, not priority order -- each step needs the ones before
it to be trustworthy. Section names refer to headers further down.

 1. Fix shrinkwrap voxelization bug (BUG section, VoxelizeFruits,
    PackShrinkWrap.cpp:277). Every distance field downstream depends on
    this; fixing it later invalidates measurements already taken.
 2. M2: verify/fix closing vs offset radius. Test on a single sphere until
    hull radius == input radius. Gates the "crust" false-positive problem.
 3. Nudge fixes N1 (step budget vs distance) and N3 (arrival / jammed /
    out-of-steps outcome). Cheap, independent of 1-2, and every settle-
    and-accept step later needs to know WHY a nudge stopped.
 4. Build VoidField helper (wraps the now-fixed ComputeShrinkWrapDistField
    + container SDF).

    SPOT MANAGEMENT), plus the debug blob-OBJ / point-cloud-PLY output.
    Stop and visually check blobs against the shrinkwrap mesh before
    writing any placement code -- cheapest point to catch a bad threshold
    or open radius.
 6. M1 histogram, reusing the width numbers from step 5. Calibrates the
    multi-scale tier and the merge test instead of guessing.
 7. ClaimGrid + TryFillSpot (SPOT-PICKS-FRUIT, kindsBySize). Needs step 4

Current PackScene order (PackingDriver.cpp:917):
  steps 0..N-2 -> free points (once) -> step N-1 -> shrinkwrap -> crevices x20

Problem with that order: free points and the deep-ray set are computed once
and consumed many times. Every fruit in the last step aims at the same
centroid, so they queue up on one spot, block each other, and stall.


CORE IDEA
---------
Two fields describe the state of the pack:

  A. container void field   = inner container SDF (already in scene.sdf)
  B. pack envelope field    = shrinkwrap dist field of placed fruits
                              (PackShrinkWrap.cpp, currently thrown away
                               after marching cubes)

The region worth filling is A_inside AND B_outside. That is a signed field,
not a point list, so it can drive search, targeting, and the stop condition
with one representation. Right now A and B are only ever used to produce
debug meshes / point clouds.

Change: have ComputeShrinkWrapDistField return the field, not just the mesh,
and keep it on the scene as scene.envelope (Array3D<short> + origin +
voxelSize + distUnit). Recompute it once per round, not once per run.

SPOT-PICKS-FRUIT (invert the placement loop for crevices and voids)
---------------------------------------------------------------------
Today: pick a fruit kind -> pick a spot for it (round-robin over
itemIndices in SeedDeepCrevices, PackingDriver.cpp:677; same shape in
Phase 2e's "for each fruit kind" loop above). That is backwards for gap
filling: the gap's size is fixed by geometry, so it should choose which
fruit fits, not the other way around.

Minimal change, reusing pieces already planned:
  1. Build kindsBySize once (item catalogue is static within a round):
       std::vector<unsigned> kindsBySize(scene.items.size());
       for (unsigned i = 0; i < scene.items.size(); i++) kindsBySize[i] = i;
       std::sort(kindsBySize.begin(), kindsBySize.end(), [&](unsigned a, unsigned b){
         return scene.items[a].BoxDiagonal() > scene.items[b].BoxDiagonal();
       });
     Include every scale tier from MULTI-SCALE FILL below as its own entry;
     they are already separate item KINDS, so this needs no special case.

  2. TryFillSpot (helper #3 above) is the new inner loop:
       int TryFillSpot(PackingScene &scene, const Vec3f &target, float localWidth,
                       const std::vector<unsigned> &kindsBySize, float clearance,
                       ClaimGrid &claims) {
         for (unsigned itemIdx : kindsBySize) {
           MeshInfo &item = scene.items[itemIdx];
           if (item.BoxDiagonal() + clearance > localWidth) continue; // too big, try smaller
           std::vector<RigidTransform> trajectory;
           RigidTransform tran;
           tran.position = target;
           tran.rotation = scene.randAngles[...]; // round-robin or random, as today
           RigidTransform settled = scene.NudgeToTarget(itemIdx, tran, target, trajectory);
           float occFrac = OccupiedFraction(scene, item.samples, settled.rotation, settled.position);
           if (occFrac < kOccupiedThresh) {
             unsigned id = scene.Put(itemIdx, settled);
             scene.instances[id].trajectory = trajectory;
             claims.Mark(settled.position, item.BoxDiagonal());
             return int(id);
           }
           // this kind didn't settle cleanly -- fall through to the next
           // smaller kind at the SAME spot, instead of abandoning the spot.
         }
         return -1;  // nothing in the catalogue fits here
       }

  3. Both passes become one shape: sort candidate spots by localWidth
     descending, then for each unclaimed spot call TryFillSpot:
       for (const Spot &s : spotsSortedByWidthDescending) {
         if (claims.IsClaimed(s.pos)) continue;
         TryFillSpot(scene, s.target, s.localWidth, kindsBySize, clearance, claims);
       }
     For Phase 2, Spot = {freePt, voidField value at freePt}. For Phase 3,
     Spot = {envelope-field-walk target (see Phase 3 above), localWidth =
     the same envelope/void sample at that point}. Same loop, same helper,
     two different spot lists -- SeedDeepCrevices and Phase 2e's per-kind
     loop both collapse into this, so there is one placement path instead
     of two independently-tuned ones.

  4. localWidth for crevices needs a real number, not just ray depth.
     Ray depth (ComputeSurfaceDepths) measures distance to the nearest
     fruit/wall along ONE direction; it is not the aperture. Once the
     envelope field exists (Phase 2a), sample it at the crevice target the
     same way Phase 2b does for voidField -- this is the same number M1
     wants for the manufacturability histogram, so it is not new
     machinery, just an earlier consumer of it.

Net effect: a crevice or void that is only big enough for the floor-sized
blueberry tier (MULTI-SCALE FILL below) automatically gets that tier
instead of stalling on a nominal-size fruit that cannot fit, and a large
open void still gets the nominal size instead of wasting a small one on it.


CANDIDATE SPOT MANAGEMENT (are two connected spots one or two, how far apart)
------------------------------------------------------------------------------
Question: how are candidate spots (freePts / crevice origins) generated and
deduplicated, and are their attraction centers spaced far enough apart.

Current state (the actual bug, not a hypothetical): candidates are dense
per-sample points, not one point per physical gap.
  - Crevices: one candidate per 0.3cm container-surface sample that passes
    FindDeepRays' local-median test. A single 3cm-wide crevice contains on
    the order of 100 such samples (its footprint at 0.3cm spacing).
  - Voids (as drafted before this pass): marching cubes at iso 0 gives one
    point per boundary triangle -- again many points per void, tracing its
    edge rather than marking its center.
  Deduplication today (crevice path only) is SeedDeepCrevices' tooClose
  check: skip a candidate within item.BoxDiagonal() of an already-placed
  position (PackingDriver.cpp:692-695). Two problems: (1) which candidate
  "wins" depends on scan order over the surface mesh, not on which one is
  actually the center of the gap; (2) the exclusion radius is the CURRENT
  fruit kind's size, not the gap's own width, so it does not adapt when a
  kind is swapped in the SPOT-PICKS-FRUIT loop above.

Fix: make a candidate spot a LOCAL MAXIMUM of the distance field
(voidField for interior voids, the same field once it also covers
near-wall space for crevices -- see Phase 3 above), not a boundary sample.
Add a cleanup pass before extracting maxima, since the thresholded mask
from 2b is jagged, not a clean set of blobs:
  - Threshold voidField per 2b's fix (voxelSize+epsilon, or the smallest
    fruit tier's radius) to get a binary mask.
  - Morphological open: erode the mask by 1-2 voxels, then dilate by the
    same amount. Erosion kills thin webs and residual crust that survived
    thresholding (jagged inflation noise, not real gaps); dilation puffs
    the surviving cores back to their real boundary. Cheap, and it is the
    same voxel grid already in hand, no new data structure.
  - Compute a fresh distance transform INSIDE the cleaned mask (distance
    to the mask's own boundary, not the raw voidField value, since the
    mask boundary shifted slightly from the open). This is the field local
    maxima are taken from.
  - Debug output, worth wiring up early since Phase 2/3 are otherwise hard
    to verify: marching cubes on the cleaned binary mask -> OBJ blobs, one
    isolated chunk per real crevice/void, with the outer sculpture surface
    absent by construction (thresholded away in 2b). And a PLY point cloud
    of the local maxima found inside those blobs -- the actual target
    positions TryFillSpot will use. Cross-check these visually against the
    shrinkwrap mesh before trusting the automated fill; a blob touching the
    outer surface, or a point cloud denser than the blob count, means the
    threshold or the open radius is still off.
  - Finding maxima: a voxel is a candidate if its field value is >= every
    neighbor in a window sized to ITS OWN value (a voxel with value w is
    only compared within roughly radius w of itself, so a deep pocket does
    not get out-competed by a shallow one several widths away that it has
    no business suppressing).
  - This directly answers "connected but one or two": a void's field
    naturally has one peak per lobe, separated by a saddle at the neck
    between them. A single round pocket integrates to one peak; a
    dumbbell-shaped void integrates to two, each with its own width. This
    falls out of the field's shape, not a tuned merge distance, so it
    stays correct as the pack fills in and the void's shape changes round
    to round.
  - Spacing between accepted maxima (non-maximum suppression): sort raw
    maxima by field value descending. Walk the list; merge a maximum into
    an already-accepted LARGER one only if their inscribed spheres already
    overlap: dist(A,B) < rA + rB. This is an EXACT test, not a tuned
    constant -- if the disks overlap, A's own free space already reaches
    into B, so they are the same feature by definition, not two features
    that happen to be near each other. If dist(A,B) >= rA + rB, keep both,
    no matter how close that is.
    Bias this test toward keeping spots, not merging them: a spot dropped
    here is a fill opportunity lost for the whole round with nothing
    downstream to recover it, whereas a spot kept that turns out to
    conflict with a neighbor is caught cheaply a few steps later (below).
    So do not round k up "to be safe" -- k=1 (disks touching) is the
    correct value, not a lower bound to pad.

  How "too close" actually gets resolved (not by this test): process the
  surviving spots widest-first (2d/2e) through TryFillSpot + ClaimGrid.
  ClaimGrid marks each spot's neighborhood using the ACTUALLY PLACED item's
  own radius the moment it settles, not a guess made at generation time.
  So if spot B was only maybe blocked by A, the answer falls out for free:
  either B still validates against OccupiedFraction (genuinely reachable,
  fill it), or it doesn't (fails or falls back to a smaller kind per
  SPOT-PICKS-FRUIT). No separate collision prediction is needed between
  spots -- the settle step is ground truth, the merge test above is not.

  How "too sparse, leaves new small crevices" actually gets resolved: by
  Phase 2 being iterated at all. The void field, the cleanup mask, and the
  maxima are recomputed every round, so any gap that opens up between two
  freshly-placed fruits -- or any spot conservatively kept-but-unfilled
  this round -- simply reappears as a fresh maximum next round, sized
  against whatever fruit tiers are still available. Nothing is lost by
  erring toward keeping spots at generation time; it only costs one extra
  round, which is far cheaper than merging away a real spot permanently.

  Refinement to keep on the shelf, not build yet: the pairwise disk-overlap
  test above is a cheap stand-in for watershed segmentation of the distance
  transform inside the cleaned mask, which is the textbook-correct way to
  decide "one blob or two" and handles elongated/asymmetric crevices (a
  long trough with two bumps) better than comparing peak centers pairwise.
  Only build it if the debug blob/point-cloud output (above) or the M1
  histogram shows the pairwise test mis-splitting real crevices.

  ClaimGrid (helper #2) should use the same PLACED-item-radius logic as
  above for claims, not a fixed constant, so a floor-sized tier does not
  over-claim a small pocket and a nominal-size fruit does not under-claim
  a large one.


MULTI-SCALE FILL (discrete blueberry sizes vs per-instance scale)
-------------------------------------------------------------------
Question: does scaling let smaller copies fill the gaps left by the nominal
size, and how do we know which radius fits a given gap.

Hard constraint: a blueberry cannot be scaled below 0.8 cm diameter and
still read as a blueberry, so this is not a free parameter down to zero.
If nominal size is, say, 1.2-1.6 cm diameter, there is room for maybe ONE
smaller tier before hitting the floor (e.g. 0.9-1.0 cm), not the 3-4 tier
range assumed below for an unconstrained filler particle. Consequences:
  - most sub-0.8cm gap volume can never be closed by a smaller instance,
    regardless of how good the void-width targeting gets. It falls through
    to the shrinkwrap closing radius (M2) or the "ignore, self-fills" bucket
    in the acceptance table by construction, not by choice.
  - the realistic win from a second tier is bounded and worth measuring
    BEFORE building the extra kind: run Phase 2 with the nominal size only,
    take the M1 histogram, and sum void volume in the 0.8-1.6 cm bucket. If
    that is a small fraction of total void volume, a second tier is not
    worth the settle time and the mesh/SDF/trigrid upkeep of another kind.
  - if a second tier is added, size it to the floor (~0.85-0.9 cm diameter),
    not to a fraction of the nominal radius -- the geometric-fraction sizing
    below assumed an unconstrained filler and does not apply once realism
    sets the floor above where the gap distribution wants the next tier.

Use discrete pre-scaled mesh KINDS, not a per-instance scale factor.
  items and kindGrids (PackingScene.h:101,127) are already cached per item
  KIND, not per instance, so adding "blueberry_0.5x" as a new entry in items
  costs exactly what adding a new fruit type costs: one TrigGrid, one SDF
  build. RigidTransform, Nudge, NudgeToTarget all work unmodified.
  True per-instance scale would need a scalar threaded through
  RigidTransform, every TrigGrid query, the broadphase bbox, contact normal
  calc, and SDF gradient sampling -- a much bigger change for a benefit the
  multi-kind route already gets, since void sizes in a random pack are not
  continuous. They cluster geometrically (the gap between near-equal spheres
  packed tightly is a fixed fraction of their radius, regardless of absolute
  scale), so a handful of discrete tiers spans the range that matters. Only
  build continuous per-instance scale if a measured gap histogram (M1) shows
  real gaps falling between the chosen tiers.

Precision needed to pick a radius for a gap: this is already planned, not
new machinery. Phase 2's voidField and "local void width" (2b/2c/2d) is the
inscribed-disk radius at each free point, at whatever resolution the field
is sampled (M5 flags today's 0.25 cm grid as too coarse below ~0.5 cm).
Matching rule for 2e: for a kind of radius r, only claim a freePt whose void
width >= 2r + clearance, and within the existing "smallest fruit kind first"
loop, try the largest kind that still fits before falling to the next size
down. One-line change to 2e's claim logic once VoidField exists.

Expected payoff, given the 0.8 cm diameter floor above:
  - the general "0.4-0.5x then 0.15-0.25x" tiering below is what an
    unconstrained filler particle would use. With a realism floor, only the
    first step is normally reachable: one tier near the floor
    (~0.85-0.9 cm diameter) recovers whatever gap volume sits in the
    0.8-1.6 cm range. That is the whole multi-scale budget here.
  - do not add a second smaller tier at all; there is no room left below the
    floor. Gaps under 0.8 cm are M2's (shrinkwrap closing radius) problem or
    self-fill per the acceptance table, not a smaller instance's.
  - so this plan's tiering rule below (unconstrained geometric fractions) is
    reference material for a filler particle without a realism floor. For
    actual blueberries, use just the two tiers: nominal, and one floor-sized
    tier, and validate with the M1 histogram whether the second tier is
    worth it at all before building it.

Unconstrained reference (particle with no minimum size), largest first:
  - one extra small tier (roughly 0.4-0.5x nominal radius) recovers most of
    the gap volume between equal spheres. Highest value single addition.
  - a second smaller tier (roughly 0.15-0.25x) picks up the small voids left
    between three touching first-tier spheres. Volume gained drops roughly
    an order of magnitude versus the first tier.
  - a third tier is rarely worth its instance count and settle time; check
    the M1 histogram before adding one.
  - below the ~0.2 cm opening threshold, do not add a mesh tier at all --
    that range is the shrinkwrap closing radius's job (M2), not more
    instances. Filling it with geometry fights M2/M3 instead of helping.


SHARED HELPERS TO FACTOR OUT
----------------------------
1. VoidField(scene, shrinkRadius) -> {Array3D<short>, origin, voxelSize,
   distUnit}. Wraps ComputeShrinkWrapDistField and the container SDF.
   Replaces both ComputeFreeContainerPoints and the ad-hoc bg.vox lookups
   in OccupiedFraction.

2. ClaimGrid: sparse voxel set of "a fruit was just placed here this round".
   Used by Phase 2e and Phase 3. Prevents the pile-up. Claim radius should
   scale with the PLACED item's own size, not a fixed constant -- see
   CANDIDATE SPOT MANAGEMENT below for why a flat radius mismatches
   between fruit tiers.

3. TryFillSpot(scene, target, localWidth, kindsBySize, clearance, claims)
   -> int instanceId or -1. Generalizes SettleAndAccept into the
   spot-picks-fruit inversion (see SPOT-PICKS-FRUIT below): tries each
   kind in kindsBySize (all item KINDS incl. scale tiers, sorted descending
   by BoxDiagonal) whose size fits localWidth, NudgeToTarget's it, and
   Puts on the first one that validates (post-settle OccupiedFraction <
   thresh). Falls through to the next smaller kind on a failed settle
   instead of giving up on the spot. On success, marks the claim grid.
   Today SeedDeepCrevices (PackingDriver.cpp:726) Puts unconditionally and
   only checks OccupiedFraction on the PRE-settle pose, so an unresolved
   overlap gets committed -- this replaces that call entirely, and also
   replaces Phase 2e's per-kind loop, so there is one accept/reject path
   instead of two.

BUG: SHRINKWRAP VOXELIZATION CUT OFF IN -XYZ
--------------------------------------------
Symptom: fruits are clipped on their -x/-y/-z sides in the shrinkwrap
occupancy grid, so the hull cuts into them.

Root cause, VoxelizeFruits (PackShrinkWrap.cpp:277). Two origin
conventions are mixed in one expression.
  AlignOriginToGrid floors to a multiple of voxelSize (GridUtils.cpp:10),
  so totalBox.vmin and every per-item bbox.vmin sit on the same lattice
  and their difference is an exact integer number of voxels.
  But outOrigin = totalBox.vmin + 0.5*voxelSize (voxel CENTER, needed by
  MarchingCubes), while conf.origin = bbox.vmin (voxel CORNER, what
  VoxConf wants). So
    (conf.origin - outOrigin)/voxelSize = n - 0.5
  and std::round of n-0.5 rounds away from zero: n for positive, n-1 for
  negative. Items whose padded bbox starts at or left of the total origin
  get shifted one voxel the wrong way; the rest do not. Hence a per-item,
  sign-dependent one-voxel error on the low side of each axis.
  The asymmetric per-item pad at PackShrinkWrap.cpp:264-265 (+1 voxel on
  vmax, -3 voxels on vmin) is a patch over this, not a fix.

Fix:
  - keep ONE lattice origin for all index math:
      gridOrigin = totalBox.vmin
      offset = RoundVec((conf.origin - gridOrigin) / voxelSize)
    which is now an exact integer, no half-voxel bias.
  - apply the +0.5*voxelSize center shift only where the field is sampled,
    i.e. at the MarchingCubes call, not in the origin used for stamping.
  - then make the per-item pad symmetric (2 voxels each side). The pad is
    only needed so FloodOutside8u has a clear border to start from: if a
    voxelized surface touches index 0 on any axis the outside flood leaks
    into the interior and the item loses its solid fill entirely.
  - assert it: after stamping, count set voxels per item and compare with
    volume/voxelSize^3. A clipped item shows up immediately.


FINAL GOAL: MANUFACTURABLE PACK
-------------------------------
The deliverable is not the fruit instances, it is one closed surface that
can be (a) CNC milled and (b) used as a master to cast a rubber mold.
The shrinkwrap mesh is the first approximation of that sculpture.

Tentative acceptance criteria, by opening size (opening = width of the
gap at the surface, not its depth):

  < 0.2 cm      ignore. mill cannot cut it, rubber will not enter it.
                these fill themselves. do not spend geometry on them.

  0.2 - 1 cm    minimize the count. any overhang under such a hole is
                auto-filled. after filling, the walls must read straight
                along the surface normal, or slightly shallower than
                straight (positive draft). never undercut.

  1 - 3 cm      must survive, and must have no overhang. these are the
                pockets the shrinkwrap is meant to shape, so the hull
                has to come out draft-clean at this scale.

  > 3 cm        real voids between fruits. these are the pack quality
                problem, handled by Phase 2 above, not by surface work.

Two conflicting requirements to keep straight: milling wants visibility
from a tool axis, rubber wants demoldability from a pull direction.
Rubber tolerates more undercut than a mill does because it stretches, so
the mill constraint is the binding one and is what should be enforced.

PHASE 3'S OWN TREATMENT OF THESE SAME BUCKETS (user, this session -- store
so this does not get relitigated or drift):
  < 0.2 cm      ignore -- self-fills, same as above.
  0.2 - 3 cm    Phase 3's actual working range (collapses the 0.2-1 and
                1-3 buckets above into one rule for THIS stage): try to
                rest one or a few appropriately-sized fruit ON TOP of the
                crevice, NOT inside it, hoping the new fruit plus its
                neighbors reduce the opening to something smaller (ideally
                into the <0.2cm bucket, but any reduction counts). This is
                the whole point of sizeMustFitLocalWidth=false in
                TryFillSpot.
  > 3 cm        ignore, for Phase 3 specifically -- not this stage's job
                (real voids between fruit are Phase 2's job with nominal-
                size fruit, per the table above; Phase 3 does not touch
                them either way).
This directly answers the voxel-size question raised while debugging
Phase 3: the whole active range (0.2-3cm) resolves comfortably on Phase
2's existing fillVoidVoxelSize=0.1cm grid (2 voxels at the narrow end, 30
at the wide end), and Phase 3 now reuses that exact grid (see PackFillVoids/
PackFillCrevices, PackingDriver.cpp) -- there is no separate Phase 3 voxel
size to tune anymore, which also removes the memory-cost argument that
justified the old container-relative field's coarser voxelSize in the
first place (see FOURTH+ ROUND corrections below).


WHAT IS MISSING FOR A MANUFACTURABLE MESH
-----------------------------------------
M1. Hole detection and classification. Nothing measures opening width
    today. Needed: for each surface cell of the shrinkwrap field, the
    radius of the largest inscribed disk across the aperture, which the
    existing distance field already almost gives. Bucket by the four
    ranges above and print a histogram. Without this number there is no
    way to tell whether a parameter change helped.

M2. Separate closing radius from offset radius. Verify what
    ComputeShrinkWrapDistField actually is. A closing (dilate r then
    erode r) fills holes up to ~2r with zero net growth. A plain offset
    grows the whole sculpture by r and sinks the fruits into it. The
    current code offsets, floods, then subtracts, which is closing-like,
    but the constants at PackShrinkWrap.cpp:214-216 mix
    shrinkRadius, 0.5*voxelSize and -2*voxelSize, so the net growth is
    not obviously zero. Measure it on a single sphere: hull radius should
    come back equal to the sphere radius, not radius+r.
    Then expose two radii: closeRadius (kill small holes) and
    growRadius (usually 0).
    Concrete symptom if this stays unmeasured: envelope - actualFruitSDF
    (or equivalently voidField > 0 at Phase 2b) will read positive
    EVERYWHERE the shrinkwrap is inflated, not just at real gaps, because
    at least 1 voxel of net growth shows up as a uniform false-positive
    "crust" over the whole sculpture surface. That crust is exactly the
    same size order as a real small crevice, so it swamps Phase 2/3's void
    detection with noise before growRadius is known to be ~0. Fixing M2
    first is a precondition for CANDIDATE SPOT MANAGEMENT below working at
    all, not an independent nice-to-have.

    MEASURED (sphere_shrinkwrap_test.cpp, new standing regression test,
    single sphere of radius 2cm, no holes to close):
      shrinkR=0.2 dx=0.1  -> hull meanR delta = 0.154 (1.54 voxels)
      shrinkR=0.5 dx=0.1  -> delta = 0.137 (1.37 voxels)
      shrinkR=1.0 dx=0.1  -> delta = 0.114 (1.14 voxels)
      shrinkR=2.0 dx=0.1  -> delta = 0.090 (0.90 voxels)
      shrinkR=0.5 dx=0.05 -> delta = 0.023 (0.45 voxels)
      shrinkR=0.5 dx=0.25 -> delta = 0.375 (1.50 voxels)
      shrinkR=0.5 dx=0.5  -> empty hull (degenerate, shrinkR==dx)

    Net growth is real (0.09-0.15cm, never near 0) but does NOT scale with
    shrinkRadius the way a broken closing-vs-offset confusion would predict
    (growth barely changes across a 10x range of shrinkRadius). It DOES
    scale with voxelSize (~1.4-1.5 voxels of extra radius at dx=0.1 and
    dx=0.25, dropping to ~0.45 voxels at dx=0.05). That points at a
    different root cause than the shrinkRadius/0.5*voxelSize/-2*voxelSize
    constants: ComputeShrinkWrapDistField's voxelization stage
    (PackShrinkWrap.cpp:183-192) marks ALL 8 corner vertices of an occupied
    voxel as dist=0, regardless of where inside that voxel the true
    surface actually passes. That is a conservative binary-occupancy test,
    not a real signed distance, and it pushes the zero-level-set outward
    by up to a full voxel before any shrinkRadius/closing math runs at
    all. The code's own comment already flags this ("coarse approximation.
    could use adapudf instead of voxelize meshes.").
    So "expose closeRadius vs growRadius" is not the right fix -- that
    framing assumes the bias scales with shrinkRadius, and it does not.
    The real fix is sub-voxel-accurate distance at the voxelization stage:
    sample each grid vertex against a real distance to the mesh surface
    (the codebase already has AdapSDF for this, used for the container
    SDF) instead of binary occupancy + corner-zeroing. Do this before
    trusting any voidField threshold derived from this field.
    sphere_shrinkwrap_test.cpp is a standing regression test for this --
    rerun it after the voxelization fix and expect delta to shrink toward
    a fraction of a voxel, independent of shrinkRadius.

    DONE. Used AdapUDF (unsigned), not AdapSDF -- signed distance needs
    reliable mesh winding to tell inside from outside, which per-fruit
    meshes do not guarantee; AdapUDF's MinDist is winding-independent.
    ComputeShrinkWrapMesh now merges all instances into one TrigMesh and
    seeds the dist field via AdapUDF::BuildTrigList/ComputeCoarseDist
    (exact point-triangle distance) instead of VoxelizeItems +
    corner-zeroing; the old closing math is unchanged, split out into
    ApplyShrinkWrapClosing so it can run on either seed. Two bugs found
    and fixed along the way, both would have crashed or silently
    corrupted results on real (non-sphere-test) data:
      - TrigMesh::ComputePseudoNormals reads the per-triangle normal array
        (nt) directly and does not compute it from current vertex
        positions; a hand-built mesh with nt never populated crashes
        (segfault) inside it. Fixed by calling mesh.ComputeTrigNormals()
        first. LoadMesh() already does this for real fruit meshes, so
        production data was never at risk from THIS specific path, but:
      - MakeTransformedMesh rotates vertex positions but never rotates nt,
        so nt on the merged multi-instance mesh is stale (wrong direction)
        for every rotated instance -- which is nearly all of them in a
        real pack. AdapDF::ComputeCoarseDist reads GetTrigNormal() (backed
        by nt) to build each triangle's frame and does not recompute it,
        so this would have silently corrupted the distance field on any
        rotated instance without crashing. Fixed by calling
        mesh.ComputeTrigNormals() on the MERGED mesh inside
        BuildUnsignedDistField, after merging/rotating, instead of
        trusting the per-instance nt that came in.

    MEASURED AFTER THE FIX (same sphere, radius 2cm):
      shrinkR=0.2 dx=0.1  -> delta = 0.039 (0.39 voxels)   [was 1.54]
      shrinkR=0.5 dx=0.1  -> delta = 0.011 (0.11 voxels)   [was 1.37]
      shrinkR=1.0 dx=0.1  -> delta = -0.055 (-0.55 voxels) [was 1.14]
      shrinkR=2.0 dx=0.1  -> delta = -0.496 (-4.96 voxels) [was 0.90]
      shrinkR=0.5 dx=0.05 -> delta = -0.062 (-1.24 voxels) [was 0.45]
      shrinkR=0.5 dx=0.25 -> delta = 0.097 (0.39 voxels)   [was 1.50]
    Net growth dropped from a consistent ~1-1.5 voxels to well under half a
    voxel across the range that matters for this project (shrinkR 0.2-0.5cm
    at dx 0.1-0.25cm). Two things NOT fully resolved, both explainable, not
    yet fixed:
      - shrinkR=1.0 and shrinkR=2.0 at dx=0.1 need band =
        shrinkRadius/voxelSize + 2 = 12 and 22 voxels; AdapDF::MAX_BAND
        caps band at 16, so the shrinkR=2.0 case silently runs with less
        band than it needs and the error grows accordingly (-4.96 voxels).
        ComputeShrinkWrapMesh already clamps to MAX_BAND rather than
        crashing, but does not warn when the clamp bites. Add a log
        warning when shrinkRadius/voxelSize + 2 > AdapDF::MAX_BAND so a
        future large-shrinkRadius call fails loud, not silently inaccurate.
      - shrinkR=0.5 at dx=0.05 (band=12, well inside the cap) still shows
        -1.24 voxels of error, worse in relative terms than dx=0.1's 0.11
        voxels despite being a finer grid. Not yet root-caused; candidates
        are icosphere facet error interacting with the closing formula's
        fixed constants (0.5*voxelSize, -2*voxelSize terms in
        ApplyShrinkWrapClosing), or distUnit=0.01cm being too coarse in
        `short` units relative to a 0.05cm voxel. Worth another sphere
        sweep at finer distUnit before relying on dx<0.1 in production.
    sphere_shrinkwrap_test.cpp stays as the regression check for both.

M3. Overhang / undercut removal. This is the largest missing piece and
    it is cheap on the grid that already exists. For a pull direction p,
    sweep the occupancy grid along p: any empty voxel that lies behind a
    solid voxel along p, and is inside the hull, becomes solid. One pass
    per axis order, O(n). That is exactly the "auto-filled overhang"
    rule stated above, and it makes hole walls straight by construction.
    Needs a decision on p: single axis (2-part mold, simplest), or a
    small set for a 4/5-axis mill. Do single axis first.

M4. Draft angle. Straight walls from M3 are the zero-draft case, which
    releases from rubber but drags on a mill and on a rigid backing
    shell. Slightly shallower than straight means eroding the fill by a
    cone instead of a cylinder: at depth d below the opening, remove
    tan(alpha)*d of wall. Same sweep as M3 with a per-layer dilation.
    Pick alpha 3-5 degrees.

M5. Voxel size is too coarse for the criteria. voxelSize is 0.25 cm
    (PackingDriver.cpp:957, SaveShrinkWrapMesh default) and the smallest
    feature that matters is 0.2 cm. Cannot classify a 0.2 cm hole on a
    0.25 cm grid. The surface stage needs 0.05-0.1 cm, which the current
    single-grid-for-everything approach will not fit in memory. Needs
    either a narrow-band field around the hull only, or a two-resolution
    pass: coarse for the pack, fine for the surface.
    Confirmed on melone_two (185 instances): shrinkRadius=0.5cm at
    voxelSize=0.25cm (ratio 2) produces visibly flat faceted sides where
    whole fruits sit underneath -- not a closing-operator bug, just too
    few voxels of margin to represent curvature within the closing
    kernel. Same radius at voxelSize=0.1cm (ratio 5) removes the
    flattening entirely. Left the production default at 0.25cm for now
    (cheap at 185 instances, unverified at "much bigger" scale) --
    resolve as part of M5's narrow-band/two-resolution design, not a
    quick default bump.

M6. Mesh conditioning after marching cubes. The output is watertight and
    manifold, which is the hard part, but it is dense and stair-stepped.
    Needed: taubin or bilaplacian smoothing that does not move the
    surface more than half a voxel (or it will reintroduce the undercuts
    M3 removed), then quadric decimation with an error bound tied to the
    0.2 cm tolerance. Re-run M1 and the M3 sweep check AFTER decimation.

M7. Minimum thickness on the rubber side. The mold is the complement of
    this mesh. Thin walls of rubber in the gaps between adjacent fruits
    will tear on demold. Same distance-field query as M1 but on the
    negative: flag complement regions thinner than ~0.3 cm and fill them
    (merging the two fruits' hulls locally), which is another argument
    for a real closing operator in M2.

M8. A base. Milling needs stock, a flat parting plane and a fixturing
    datum; pouring rubber needs a level rim. Nothing in the pipeline
    establishes an orientation or a base plane. Needed: choose the pull
    direction p (M3) and the parting plane together, then boolean the
    hull against a half-space and add a skirt.

M9. A verification report, run every time, that either passes or fails:
    hole histogram by bucket, undercut voxel count for p, draft
    violations, min complement thickness, and whether the mesh is
    closed and self-intersection-free. Manufacturability is a set of
    inequalities, so it should be checked mechanically, not by looking
    at the mesh.

Suggested order: M2 (know what the operator does) -> M1 (be able to
measure) -> M3 (the actual fix) -> M9 (keep it fixed) -> M5 -> M4 -> M6
-> M7 -> M8.


NUDGE NOTES  (answers "is the physical nudge code correct")
----------------------------------------------------------
Short answer: the solver is sound, the driving is not. Fruits stop halfway
because they run out of steps and because the target is often unreachable,
not because the contact response is wrong.

N1. Step budget vs distance. PackingScene.cpp:1272 nudgeAcceleration=200,
    dt=1/60, damping 0.82-0.85. Terminal speed = a*dt*d/(1-d) ~= 19 cm/s,
    so ~0.31 cm of travel per step. SetSimParams (PackingScene.cpp:640)
    gives steps=30 for minExtent<3. Max reach ~9 cm, and that assumes no
    contacts. Targets from NearestKCenter are routinely 10-30 cm away.
    The fruit stops mid-flight with velocity still high.
    Fix: in NudgeToTarget, size the step count from the initial distance,
    steps = clamp(dist / (v_term*dt) * 1.5, 30, 400), and exit on
    arrival (dist < eps_arrive) rather than only on low velocity.

    DONE. maxSteps = max(simParams.steps, min(400, 1.5*initialDist/(vTerm*dt)))
    in NudgeToTarget (PackingScene.cpp), vTerm = nudgeAcceleration*dt*damping/
    (1-damping) per the formula above. Loop also now checks dist < epsArrive
    (epsArrive = ds, the per-size contact tolerance already computed) at the
    top of each step and breaks with outcome=Arrived, instead of relying on
    the low-velocity break to also mean "got there". On melone_test's real
    pack, most settles still land at steps=30/30 (initial distance was small
    enough that the existing 30-step floor already covered it), confirming
    this is additive, not a behavior change for short moves; long-distance
    crevice targets now get more steps when they need them instead of being
    silently truncated.

N2. Velocity cap fights the pull. SolveContactConstraintsPGS
    (PackingScene.cpp:537) caps approach speed at
    -(distance - eps)/dt. With activeBuffer = ds = 0.2 and eps = 0.02 that
    is 10.8 cm/s, well under the 19 cm/s terminal speed. Any contact in
    the buffer throttles motion along its normal to about half speed, so
    a fruit sliding down a wall covers half the ground the step budget
    assumed. Compounds N1.
    Fix: keep the cap (it is what stops tunneling) but account for it in
    the step budget, or raise activeBuffer only for the gather and use a
    tighter distance for the cap.

N3. Early exit cannot tell "arrived" from "jammed".
    PackingScene.cpp:1382 breaks when both velocities are small. A fruit
    wedged against a wall with the spring pulling straight into the wall
    has near-zero velocity on step 2 and exits immediately, one step from
    where it started. Caller then Puts it there.
    Fix: return an outcome (arrived / jammed / out-of-steps) so the caller
    can retry with the next-best target instead of committing a bad spot.

    DONE. Added enum class NudgeOutcome {Arrived, Jammed, OutOfSteps}
    (PackingScene.h) and an optional NudgeOutcome *outcome out-param on
    NudgeToTarget. Jammed vs Arrived is decided at the existing low-velocity
    break by re-checking distance to target against epsArrive, so a fruit
    that stalls right next to its target is not reported the same as one
    that stalled far short. Full TryFillSpot-style retry-on-Jammed (helper
    #3) is still future work (step 7), but SeedDeepCrevices
    (PackingDriver.cpp) already uses the outcome for something concrete now:
    it re-checks OccupiedFraction on the POST-settle pose before committing,
    where before it only checked the PRE-settle pose and Put unconditionally
    -- exactly the bug flagged in SHARED HELPERS #3 ("an unresolved overlap
    gets committed"). On melone_test's real pack this post-settle check
    fired and skipped 62 placements that the pre-settle check had missed.

N4. Target is behind the fruit in the crevice path.
    SeedDeepCrevices (PackingDriver.cpp:710) places the fruit at
    O + dir*(0.5 + 0.5*diag), i.e. already inside, then targets
    NearestKCenter(surfacePoints, O, 5) which is a centroid of points near
    O, i.e. near the wall it just came from. The pull is backwards. The
    fruit moves a little, hits the wall, and stalls. This is the most
    visible "stops halfway".
    Fix: target a point further along the ray, e.g. O + dir*depth*0.5.
    Once the envelope field (Phase 2) exists, do this by sampling the field
    along the ray and stopping just short of where it crosses zero, so the
    target is guaranteed reachable open space, not a fixed 0.5*depth guess.

N5. Centroid of 5 surface points is not guaranteed to be free space.
    NearestKCenter (PackingDriver.cpp:22) averages positions on a curved
    inner surface, so on a concave corner the centroid lands inside the
    wall, and on a convex bulge it lands outside the container. The fruit
    then pushes into geometry it can never reach.
    Fix: drop NearestKCenter for this purpose. Use the same envelope-field
    walk as N4's fix instead of averaging points at all -- a field lookup
    cannot land inside a wall or outside the container by construction,
    where an average of surface points can.

N6. Stale contacts are applied at stale positions.
    contactGatherInterval=2 for 3-5 cm fruits (PackingScene.cpp:652).
    Contact.worldPos is captured at gather time and reused next step
    (PackingScene.cpp:1361), so the lever arm r = worldPos - currentT is
    wrong by one step of motion, which injects spurious torque.
    Fix: either gather every step for these sizes, or store contacts in
    body-local coordinates and re-project each step.

N7. Constant-magnitude pull, not a spring. PackingScene.cpp:1319 normalizes
    toTarget, so force does not fall off near the target. With damping it
    settles rather than orbiting, so this is survivable, but there is no
    braking and no arrival test. Pairs with N3.

N8. Minor: minVel is compared against squared speed
    (PackingScene.cpp:1382) while the name and the 1e-3/1e-4 values read
    like a speed. Effective thresholds are 0.032 and 0.01 cm/s. Rename to
    minVelSq or square at use, so tuning it does what the tuner expects.

Priority: N4 and N1 first, they explain the reported symptom directly.
N3 next, it stops bad placements from being committed. Then the Phase 2
re-derivation, which is what makes the last step actually fill holes
instead of queueing every fruit at one centroid.

- Pore network extraction / "maximal ball" algorithms (rock physics,
  porous media): Silin & Patzek; Al-Kharusi & Blunt, "Extracting Pore
  Network Model from micro-CT Images of Sandstone". Same problem as
  CANDIDATE SPOT MANAGEMENT above -- local maxima of a distance transform
  as pore/void centers, merged by inscribed-sphere overlap, connected into
  a network by throats. Their watershed-based merge refinement is the
  citable version of the "shelf item" noted there if the pairwise disk
  test proves too crude on real crevice shapes.

- Polydisperse / bidisperse hard-sphere packing density. Ordered-lattice
  void radii are exact and a useful sanity check: FCC/HCP octahedral void
  inscribes 0.414r, tetrahedral void inscribes 0.225r (r = the large
  sphere radius). For random packings, Kansal, Torquato & Stillinger's
  polydisperse hard-sphere packing work and the broader bidisperse-density
  literature give a measured optimum large:small diameter ratio (roughly
  5:1-7:1 for a binary mix) for maximum density -- a literature-backed
  number to check the MULTI-SCALE FILL tiers against, rather than the
  0.4-0.5x / 0.15-0.25x guess used there.

- Ellipsoid jamming: Donev et al., "Improving the Density of Jammed
  Disordered Packings Using Ellipsoids" (Science, 2004). Random close
  packing density ~0.64 (spheres, Bernal) rises to ~0.71 for ellipsoids
  purely from the added rotational degree of freedom letting particles
  rotate into gaps a sphere cannot. Directly argues for letting
  Nudge/NudgeToTarget exploit rotation aggressively during settling, not
  just as a random initial pose, if items are approximated as ellipsoids.
  Torquato & Stillinger, "Jammed Hard-Particle Packings: From Kepler to
  Bernal and Beyond" (Rev. Mod. Phys., 2010) is a good single survey tying
  RCP, jamming criteria, and the ellipsoid result together.

- Moldability / undercut / parting-direction analysis (CAD literature):
  search terms "moldability analysis," "parting direction computation,"
  "undercut detection ray casting." The core M3 technique (sweep occupancy
  along a candidate pull direction, shadowed voxels are undercuts) is a
  studied CAD problem; that literature mainly adds smarter parting-
  direction selection when a single axis is not good enough, relevant to
  M8's base/parting-plane choice.
